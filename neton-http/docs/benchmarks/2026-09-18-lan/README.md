# Baseline 双机内网对照（2026-09-18）

## 测量边界

- 两台独立 Fedora 44 虚拟机，服务端和负载端各 16 vCPU / 32 GiB；来宾拓扑为 8 核、每核 2 线程，不是 16 个物理核。流量走内网。
- HttpArena 源码 `758c775a64960f778fe0b136cecf1b45c31d1a8a`。正式复验直接运行原始 `scripts/benchmark.sh neton baseline`，不修改 profile、三个 raw 请求或结果解析。
- 参数为 4096 连接、16 个负载线程、pipeline=1、每轮 5 秒、每组 3 轮；默认 profile 的 CPU 集合超过本机范围，原脚本自动限制到本机 16 vCPU。负载命令通过受限 SSH 代理在另一台机器执行。
- 使用 gcannon v0.5.3，源码 `43b30bc24c8cc6aab37dd7d718b47ffb985e6558`，liburing 2.9。拆分请求、worker 和代码候选的筛选使用相同 raw 请求及参数，但筛选脚本不是 Arena 主脚本；原始日志分别保留。
- Docker Hub 不可达，因此没有按原 Dockerfile 构建镜像：Neton 使用本机交叉编译的 Maven beta18 入口；Actix 使用同一份 Arena 入口在服务端以 Rust 1.98.1 和 `target-cpu=native` 编译。二者打包服务端 Fedora 共享库进入运行镜像。这是本机对照，**不是完整复现 Arena 排名环境**。
- 没有发布 Maven、推送 PR、执行 `--save` 或修改公开成绩。不能将这里的绝对 RPS 与 Arena 的百万级结果直接相减。

## 原始对照

| 官方 profile，三轮最佳值 | Neton beta18 | Actix |
|---|---:|---:|
| baseline | 375,521 RPS | 732,835 RPS |
| limited-conn（本轮后续不再优化） | 303,524 RPS | 533,737 RPS |

原始日志见 `raw/arena-*.log`。完成响应的状态码为 2xx，`Per-template-ok` 与对应模板完成计数一致；测试结束时请求数与响应数的差值不能直接当成失败数。

拆开 raw 模板测试后，Neton 的 GET 为 387–398K、定长 POST 为 370–377K、chunked POST 为 351–354K；Actix 分别为 807–822K、713–724K、690–705K。因此差距不只存在于 chunked。混合测试的模板完成数不均衡也不能独自证明 chunked 解析器故障。

## 已确认的局部收益：固定响应头编码复用

只在恰好一个 `Content-Type`、恰好一个值且匹配四种固定常用媒体类型时，复用私有编码字节。不是缓存响应体或业务结果。Cookie、CORS、多值、非 ASCII、自定义类型及原始名称大小写均走原编码路径。

控制版使用 hyper4k `01898659dd94e4635ad42b50287688a206ec8e03` 的干净源码；候选只加入这一项改动。两者使用同一编译链、Arena 入口和配置。没有把工作区原有的请求字符串 scratch 实验带进对照。

正式复验顺序 A/B/B/A，每组均由原始 Arena 主脚本运行三轮：

| 组 | 三轮 RPS（K） | 脚本报告的最佳值 |
|---|---|---:|
| A 原版 | 357.94 / 371.89 / 369.60 | 371,932 |
| B 响应头复用 | 366.58 / 385.69 / 380.83 | 385,739 |
| B 响应头复用 | 372.96 / 386.56 / 392.62 | 392,669 |
| A 原版 | 361.08 / 373.21 / 372.39 | 373,258 |

六个样本中位数约 **370.75K → 383.26K（+3.4%）**。两组最佳值均值约 +4.5%。仅支持这台机器和本轮条件下的局部收益，**没有追平 Actix，也不承诺在 Arena 同幅提升**。内存仍约 1 GiB。

## 未采用的实验

**筛选脚本纠错：** 早期自定义筛选及 perf 脚本错误地重复传了三个 `--raw`，gcannon 会覆盖而不是追加，实际只运行最后的 chunked POST。下面的旧筛选数字仅适用于单模板，不能称为完整 baseline。原始 Arena 主脚本的初始对照和上面的 A/B/B/A 复验不受影响，日志明确有 `Templates: 3` 与三项 `Per-template-ok`。修正脚本后使用逗号列表，且强制检查三模板标记；重测日志使用 `mixed-` 前缀。

- `TCP_NODELAY`：通过仅作用于实验容器的 accept 拦截探针，约 +1%，尾延迟没有稳定改善；不作为已确认的修复。
- worker 数：旧单模板筛选中 16 优于 4、8、32、64，保持默认。不从线程数推导 CPU 瓶颈。
- 合并信号量和活跃请求计数：四轮中位数约 360.41K → 360.46K，未确认收益，生产代码恢复原实现。
- 协程父任务分片：仅在隔离构建目录实验，四轮结果重叠，约 +0.6%；没有加入框架。不能因此断言其他规模没有竞争。

### 修正后的三模板筛选

所有 `mixed-*.log` 都必须包含 `Templates: 3` 和三项 `Per-template-ok`。正序再倒序，每个候选两轮，只作筛选，不足以证明百分之一量级的收益。

| 候选 | 两轮 RPS（K） |
|---|---|
| 已保留的响应头优化 | 373.07 / 367.18 |
| 再合并计数 | 372.35 / 377.63 |
| 再分片父任务（基于合并计数版） | 385.42 / 377.86 |
| 单块请求体聚合（基于响应头版） | 373.67 / 378.61 |
| PMCS（基于请求体版） | 378.11 / 381.53 |
| 监听 backlog=65535（探针，基于响应头版） | 354.89 / 351.69 |
| TCP_NODELAY（探针，基于响应头版） | 376.11 / 374.12 |
| 8 workers（基于响应头版） | 330.42 / 329.45 |
| 32 workers（基于响应头版） | 351.67 / 360.24 |

没有将以上候选加入正式代码。请求体候选的补丁保存在 `tools/request-body-*.patch`，通过正确性测试不等于证明提速。

监听队列的证据比 CPU 符号归因更明确：当前 mio 1.2.1 源码默认 backlog=128；`mixed-*.json` 中 `ss` 也显示 128。两次放大队列的实际值为 65535，`TcpExt.ListenOverflows/ListenDrops` 增量都为 0；响应头控制版两次为 18,501 和 16,184。计数是内核事件，不是唯一失败请求数。放大队列消除溢出，但本次吞吐下降，不能宣称它已经解决 baseline 性能问题，更不能通过故意缩小队列提高成绩。

GC 对照通过二进制符号确认 CMS/PMCS 确实切换，不只看构建命令。当前默认 CMS 与 PMCS 选项见 [Kotlin 官方内存管理文档](https://kotlinlang.org/docs/native-memory-manager.html)。旧单 chunked 模板的 30 秒对照为 CMS 352.56/359.60K、PMCS 365.98/364.36K，两者都记录了超过 5 秒的延迟样本；Actix 同模板为 706.93/711.02K。这个结果不能外推为完整 baseline 的 GC 收益，因此没有更改默认 GC。

## 代码与测试

- 响应头测试覆盖固定类型、多值、额外 Cookie、大小写和源 map 后续变更。
- 新增并发入口测试：8 个线程提交 128 个请求，上限 7，验证拒绝数量及每个请求恰好一次完成，重复 10 轮。保留原信号量也通过。
- 请求体单块聚合候选的 Rust 全量测试：141 通过、2 个外部测试忽略。
- Kotlin 全量复验曾出现一次已有客户端背压测试超时；单测重跑通过，随后完整测试二进制连续三轮各 52 项通过。不能抹去那次失败，也未证明其原因；发版前仍需关注该不稳定用例。
- 撤回未采用的请求体和并发计数改动后，最终保留代码的 `macosArm64Test` 再次通过，52 项。

## 收尾与后续

本轮容器已停止，两个主机的临时 socket sysctl 已按各自备份恢复；服务端临时防火墙表已删除，负载端的受限压测公钥授权与服务端对应私钥已移除。测试工具、镜像和原始证据保留以便复跑，没有发布版本。

修正后的三模板采样中，Neton 的 Sweep 自耗时约 3.11%、Allocate 约 2.18%，请求处理、协议解析和编解码成本分散在多个符号中。这不能证明 GC 或某个全局锁是主要瓶颈。下一步应以相同三模板负载拆分 Kotlin 请求/响应桥接与完整分发路径，并复验低分配实现；不要仅依据单个符号排名或增加线程数决定架构改动。
